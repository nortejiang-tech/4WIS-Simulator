## 1. 判断标准：什么叫"专业级可交付"

一个转向系统开发工具，要能被下面这几类人在**日常工作**里用上，而不是只能看演示：

| 角色 | 他每天要做的事 | 今天能做吗 |
|---|---|---|
| 转向控制工程师 | 调助力曲线、阻尼、主动回正、摩擦补偿；SBW 路感与角度跟踪 | ❌ 没有扭矩传感器信号，也没有助力曲线这个对象 |
| 机械/选型工程师 | 按最恶劣工况定电机扭矩/功率、减速比、齿条力包络、热 | ⚠️ 有准静态齿条力，没有电机与占空比 |
| 整车动力学工程师 | 不足转向梯度、瞬态响应、中心区手感、KC 影响 | ⚠️ 车辆侧很强，中心区手感缺（要手力矩） |
| RWS/4WIS 工程师 | 后轮比例调度、同相/反相切换、角度权限、协同律 | ✅ 这块是现有强项 |
| 功能安全工程师 | 失效模式、降级、FTTI、ASIL 论证 | ⚠️ 有故障注入与一份研究，没有工作流 |
| 试验/标定工程师 | 按标准跑客观试验、与实车对标 | ⚠️ 有部分工况，缺转向专用标准与对标闭环 |

**结论：车辆侧已经够专业，转向系统侧还停在"诊断输出"。**

## 2. 核心判断：转向系统没有被建模成被控对象

后端全量检索：`torsion` / `torque_sensor` / `assist` / `back_emf` / `worm` / `ball_screw` /
`thermal` / `current_limit` 命中数**均为 0**。

现有链路：

```
归一化输入 →〔手感层 i(v) + μ 软限位〕→ δ_cmd →〔一阶滞后 τ + 速率限〕→ δ_actual
                                                                          ↓
                                             轮胎力 → 主销力矩 τ_steer → 齿条力（诊断）
```

主销那一段质量很高（`kingpin.py`，Reimpell 口径，机械/气胎拖距分离且防重复计入）。
**但它是链条的终点。** 缺的是从方向盘到齿条的整个系统：

```
θ_sw, τ_driver
  └ 转向柱 J_c、摩擦、扭杆 K_tb  →  τ_sensor = K_tb·(θ_sw − θ_pinion)   ← 所有 EPS 控制律的输入
       └ 助力曲线 τ_assist = f(τ_sensor, v, …)                          ← 最核心的可标定对象
            └ 电机 J_m, K_t, R, L, 电流限, 热降额
                 └ 减速机构 N, η_正/η_逆（可逆驱动性）
                      └ 齿条 质量、库仑+粘性摩擦、柔度
                           └ 拉杆 → 主销 → 车轮                          ← 已存在
```

缺这一段的直接后果：**助力曲线无从开发、电机无从选型、手力矩算不出来因此中心区手感
指标（ISO 13674）全部无法计算、SBW 路感没有东西可反馈。**

而这一段恰好是 EPS→SBW→RWS→4WIS 的**同一根主轴**：补上它，四者是同一套被控对象的不同
拓扑配置；不补，它们只能是四个并列的策略名字。

## 3. 目标架构（v2）

### A. 转向系统被控对象层（新增，最重）

新包 `backend/src/sim4wis/steering/`，与 `vehicle/` 平级：

- `column.py` — 柱惯量/摩擦/扭杆，输出 `torque_sensor` 通道
- `assist.py` — 助力曲线（查表 + 插值 + 车速维），可标定、可版本化、可 sweep
- `motor.py` — 电磁 + 机械 + 电流限 + 热降额，输出转矩-转速工作点
- `gear.py` — 减速比与正/逆效率（可逆驱动性决定路感与回正）
- `rack.py` — 齿条质量、库仑/粘性摩擦、柔度
- `topology.py` — 把上面几件按架构接成一条链

**必须是可选层，默认关闭。** 与仓库既有做法一致（"k=0 与 σ=0 保持 no-op"）：
不启用时行为与今天逐位一致，golden 不动。

### B. 架构成为一等配置

今天 `strategy` 把"架构"和"控制律"混在一起。v2 拆开：

| 架构 | 拓扑 | 特有失效模式 |
|---|---|---|
| C-EPS / P-EPS / DP-EPS / R-EPS | 机械柱 + 助力点位置不同 | 助力丢失、过助力、自转向、振荡 |
| SBW | 无机械路径；路感作动器 + 前轮作动器；角度跟踪 | 通信丢失、角度偏差、冗余切换 |
| 机械 + RWS | 前机械/EPS + 后轴作动器 | 后轮卡死/失权（已有研究） |
| SBW + RWS | 全线控前后 | 组合失效 |
| 4WIS | 四角独立 | 单轮失效（已有研究） |

选架构 → 决定拓扑、传感器集、作动器集、可用失效模式、可算指标。**能力边界守卫
（study 层 P2）天然扩展到这里**：问 C-EPS 要"后轮相位"应当被拒绝而不是返回 0。

### C. 客观试验与指标库（对标标准）

现有工况：直线、圆弧、八字、绕桩、ISO 3888-1/-2、ISO 4138 skidpad、泊车。
补齐转向专用的：

| 标准 | 试验 | 关键指标 | 依赖 |
|---|---|---|---|
| ISO 13674-1/2 | 中心区 weave | 力矩梯度、力矩死区、迟滞、摩擦感、横摆相位滞后 | **需要 A** |
| ISO 7401 | 阶跃 / 正弦扫频 | 横摆增益、相位、共振频率、响应时间 | 部分已有（`sweep` 激励已存在，缺指标） |
| — | 回正性 | 残余角、回正速度、超调 | **需要 A** |
| — | 原地/低速转向力 | 峰值手力矩、齿条力、电机峰值扭矩 | **需要 A** |
| — | 摩擦/迟滞环 | 力矩-角度环面积 | **需要 A** |

全部落成 study 层的 **spec 模板 + 指标集 + 目标带**，不是新写一套东西。

### D. 目标 / 需求层（新增）

一个可版本化的 `targets/` 库：每个指标 × 每个工况点的目标带。
study 层的 `criteria` 升级为"目标符合性报告"——一张表回答**这套转向配置达标了吗**。
这是交付给团队时最直接的价值：不是"跑出一堆曲线"，而是"对着目标判定"。

### E. 选型与包络

扩展现有负载页：电机转矩-转速包络、占空比、热；最恶劣工况矩阵（高附原地、路缘冲击、
对开路面、单侧上台阶）；产出一页**作动器规格书**。

### F. 功能安全工作流

把现有故障注入扩展到新被控对象（助力丢失、自转向、振荡、传感器故障、过助力），
加降级时序与 FTTI，报告模板化。已有的单轮失效研究成为其中一个实例而不是孤例。

### G. 可交付性与可信度

- 按角色的入口（控制 / 机械 / 安全 / 试验），而不是七个并列页签
- 说明书按角色重构（现有 `build_manual.py` 自动生成的底座可用）
- 单位与口径约定文档化
- **可信度见 §6**

## 6. 绕不开的一关：可信度

`scripts/check_v1_readiness.py` 现在报 **NOT READY**，唯一未过的严格门禁是
`independent_reference`——**没有任何通过检查的独立外部/实测参照**（CarSim/CarMaker、
台架、缩比车或实车 benchmark）。

交付给公司团队时，第一个被问的问题必然是"这东西准不准"。今天能诚实回答的是：
内部一致性好、与闭式解对得上（study 层验收 0.13–1.10%）、golden 逐位可复现。
**不能**回答的是：与真车或商业工具对得上。

三条路，需要你选：

1. **实车/台架数据**——若公司有转向台架或实车试验数据，接进 `validation_data/`，
   门禁自然转绿。这是最有价值的一条，也最依赖你那边的资源。
2. **商业工具对标**——若公司有 CarSim/CarMaker license，用同一组工况对拉。
3. **明确限定声明**——不做外部对标，但把边界写进**产品界面本身**（不是只写在文档里），
   例如启动页与报告页固定显示"本工具经解析闭式解与内部一致性验证，未经实车相关性验证"。

我的建议：**先走 3 保证诚实，同时推 1**。3 是零成本且必须做的（否则同事会默认它是
经过实车验证的）；1 是让这个工具从"很好的内部仿真"变成"可依据的开发工具"的唯一途径。

## 8. 已定（2026-08-11）

- **a. 架构优先级：R-EPS/C-EPS → SBW → RWS。** 主轴顺序，RWS/4WIS 侧最后接。
- **b. 可信度先留空**，后续有机会补充台架、整车与仿真数据。
  → 因此 §6 的第 3 条（界面级边界声明）**现在就做，且是必做项**：在没有外部对标之前，
  产品必须自己说清楚它没被实车验证过，否则同事会默认它验证过。第 1 条留出接口，
  数据到位即可转绿，不需要返工。
- **c. 第一批用户：系统工程师。** 这条改了期次顺序，见下。
- **d. 后轮转角权限变成真的 `VehicleParams` 字段。** 架构层本来就要描述后轴作动器的
  角度权限，顺带让车辆页那个从不被读的 `rear_rack_travel_limit` 有归宿。
- **e. 版本号 v2.0**，v1.0 跳过。

### c 带来的顺序调整

系统工程师的日常是**架构取舍、需求分解、选型定规格、接口定义、失效分配**——不是调助力
曲线的细节（那是控制工程师）。所以原定的 V3（ISO 试验指标）与 V4（目标+选型）对调：

    V1 被控对象 → V2 架构 → **V4 目标层 + 选型包络** → V3 试验与指标库 → V5 安全 → V6 交付

理由：系统工程师拿到 V1+V2+V4 就已经能干活了——在同一台车上把 EPS / SBW / +RWS 摆在
一起，用同一套判据比，然后输出一页作动器规格书。V3 的中心区手感指标更多是控制与
试验工程师的工具，往后放一期不挡他们。

V6 的角色入口也据此排：**系统工程师视图为默认入口**。

#### 下一步：把 plant 接进前轴

这是 v2 里风险最高的一步——它动的是全仓最容易悄悄改变既有行为的地方。**先立护栏，再动通路。**

### 9.2 线控前轴通路（已完成）

`steering/bywire.py`。线控的两个作动器彼此独立、只靠软件相连：

- **前轮作动器**：带宽受限的角度跟踪 + 速率限；`angle_deviation` 被监视而非假定为小——
  它是发现作动器饱和/堵转/缺相的手段，也是架构注册表里那个失效模式的触发量。
- **反馈作动器**：手力矩是**合成**的，不是测量的。路感项（齿条力经低通）+ 回正项
  （速度调度，线控没有主销回正力矩传到手上，不给就不回正）+ 阻尼 + 少量摩擦，
  最后被反馈电机能力钳位。

**已知限制（写在测试里）**：路感低通目前是一阶，6 Hz 转折处对 20 Hz 冲击只能衰减到
1/3.4（−20 dB/decade 就这么多）。量产路感设计用更陡的滤波。**如果将来要用这个模型
回答真实的冲击抑制问题，这是第一个必须改的地方。**

### 仍然成立的边界

被控对象层的数值是**合理但未验证**——没有台架或实车数据背书，参数是工程估计。
按 §8 决定 b，这条边界必须在接入的同时进入产品界面，而不是只写在文档里。
