01

一、起点：一页需求

项目从零到现在唯一的书面原始需求，是一份不到 20 行的 Markdown 文件。下面是它的全文——今天平台的每一个模型、每一条策略、每一次安全研究，都是从这五段话生长出来的。

  1. 前端需要是网页版的形式，以确保可以在 Windows 和 Mac 上面都可以正常运行。
  2. 可视化仿真的操控方式需要至少包含四种：键盘操控方向盘转角和车速；通过脚本/动作序列规定方向盘角度和车速；规定行驶轨迹（手动搭建或标准化路径模块拼接）；未来可扩展——通过 USB 模拟设备（方向盘、手柄）控制车辆。
  3. 仿真过程中需要能实时观测每个车轮的转角、转向阻力矩、每个车轮的转向中心和整车瞬心的显示，并将可实现部分以曲线记录。
  4. 悬架参数（主销后倾角、主销内倾角、车轮外倾角、车轮尺寸等运动学/动力学相关参数）需要可按需调整并按项目保存。
  5. 需要可以手动在可视化仿真路线中增加扰动设置，比如减速带、斜坡路、对开路面等。
全文引自 4WIS Simulator 功能需求.md，写于 2026-06-19（squash 基线时间戳），是项目全程唯一的正式需求文档——没有 PRD、没有原型图，后续所有功能都由"需求 + 实测反馈 + 工程复核"迭代出来。

需求条目 2 的伏笔

"USB 模拟设备（方向盘、手柄）"当时被明确标注为"未来可扩展"、因缺硬件而暂缓。它在 v0.9.0 首次以 Web Gamepad API 落地，v0.15.0 才真正长成一套"轴 → 车轮分组"的通用绑定机制——从提出到完整实现，跨越了项目近全程。

需求之外的背景研究

仓库根目录同期还留有一份《四轮独立转向解耦控制系统：挑战与方案研究》背景资料。这提示项目动机不只是"做一个仿真器"，而是服务于 4WIS 解耦控制这一更大的工程研究命题——仿真平台是研究这个命题的工具，不是目的本身。

需求条目 3 的完成度

"每个车轮的转向中心"这一条在 v0.1.0 尚未实现，直到 v0.4.0 才作为"需求补全"专项补上——瞬心投影、带符号偏差、超限变红、CSV 通道全部到位，距最初提出过了约 20 天。

四、八个开发阶段

按叙事而非严格版本号切分为八个阶段。每个阶段先讲背景与交付，遇到的核心难点在标注处展开、并在下一节做完整的技术复盘。

ERA A

起步三部曲

2026-05-23 → 05-25 · v0.1.0–v0.3.0

三天内从零搭出可跑的 4WIS 仿真骨架：运动学模型、控制策略、可视化、记录、3D、多体动力学、便携分发全部到位。Phase 划分严格对应需求文档的展开顺序。

v0.1.005-23Phase 1 · 运动学基座

运动学 4WIS 模型；5 种控制策略（含理想阿克曼解析解，四轮瞬心严格共点、零滑移）；WebSocket 状态流 /ws/state；2D 可视化；YAML 项目文件。

v0.2.005-24Phase 2 · 记录与扰动

Recording/CSV 导出；μ 路面扰动；YAML 动作脚本；简化动力学模型；悬架阻力矩；减速带/斜坡扰动；FMU/MATLAB 适配器；smoke 测试 24 项。同日用户手测反馈 5 个问题，团队产出系统性根因分析文档，明确排到 Phase 3 交付后再统一处理。

v0.3.005-25Phase 3 · 3D、多体、便携包

3D 可视化（Three.js）；轨迹编辑器 + pure-pursuit 跟踪；14 自由度多体动力学；A/B 双跑对比；路面摩擦预设；定速巡航 + 回正速度滑块；转向作动器一阶滞后；深浅主题；便携一键启动包。同版完成 P0/P1/P2 三批改进（键盘保持模式、对开路面 μ 可视化、减速带数值修正、脚本↔路桩关联、kingpin 力矩单调性修复、系统性轮胎/伺服标定）；默认车型换装智己 LS9；后端端口 8000→8010 避让本机 LLM 服务；摩擦系数改绝对值语义。

难点提要

键盘归零导致无法定速/定转角、对开路面"μ 锁存"疑云、减速带数值发散、kingpin 力矩非单调、中速甩尾疑似模型发散——六个问题里五个是标定/语义问题，一个是真 bug，详见 §五「假警报陷阱」。

ERA D

统一物理底座

2026-06-20 → 06-21 · v0.8.0–v0.8.2

一次完整的底盘动力学 review 之后，团队决定不再继续"加功能"，先解决物理散落在五处、单轮 sweep 看不见车速依赖这两个根本问题。这一阶段也是项目第一次推送到 GitHub。

v0.8.006-20model_core 统一底座 + bicycle 耦合 + 讲解页

vehicle/model_core.py 成为唯一共享数学层；tire.pacejka_combined_forces 统一轮胎内核；kingpin 力矩四项分解；model_registry 模型注册中心（primary 两层 + research 多体）；W1 稳态 bicycle 耦合——单轮 sweep 不再假设车身锁直行；载荷敏感刚度 c_α(Fz)；新增"数学模型"讲解页（10 章 + 9 张教学 SVG + 3 个交互 demo，只读教学端点复用真实底座）。本版由人机异步接力完成——用户离线期间 Codex 先做完底座统一，回来后再接力 bicycle 耦合与讲解页。测试 144 → 161，首次 squash 推送 GitHub。

v0.8.106-20body_coupling 口径开关

W1 bicycle 耦合让单轮 sweep 更贴近驾驶手感，但工程师另有"无论车身怎么响应，单轮自己要扛住多少力"的选型需求。新增 body_coupling 参数（vehicle 整车装载 / isolated 单轮台架），贯穿 sweep、敏感度、kingpin 分解 demo 全链路，两种口径共存而非二选一。测试 167。

v0.8.206-21kingpin 气胎拖距重复计算修正

依据姊妹项目《底盘与转向动力学讲义》交叉核对《Steering Handbook》时，发现气胎拖距被结构性计入两次、符号相反几乎完全抵消，且抵消最严重的区间正是 δ_eq 所在的小转角区。修正后气胎拖距只经 Mz 一条通道进入且与机械拖距同向叠加。同时完成负载页/工作台 UX 层级增强、新增可关闭"快速开始"引导卡。测试 168。

难点提要

物理"重复造轮子"与单轮 sweep 的车速盲区、一个 kingpin 力矩公式的三次迭代订正。均在 §五 有完整复盘。

ERA F

安全研究实战

2026-07-02 → 07-03 · v0.13.0–v0.14.0

平台化重构完成主干的当天，就拿它做了第一个"真研究"：单轮转向失效的 ISO 26262 可控性定量分析。这不是又一个功能，而是对整套实验-运行-资产主干的第一次实战检验。

v0.13.007-02单轮失效安全研究首发

01

假警报陷阱：把"语义误用"误诊为"模型物理发散"

v0.3.0 前v0.6.0标定 / 控制器

现象

至少两次，团队观察到"车辆在某工况下产生了物理上不合理的巨大侧滑并持续打转"，第一反应都是怀疑动力学模型或轮胎标定错了。

案例一 · 真实标定问题

μ=0.9、恒定转向 0.25、中速行驶时，简化动力学模型出现 vy≈−7.8 m/s 的巨大侧滑并持续打转。排查后确认是 LinearTireModel 刚度、轮速伺服增益、无转向速率限制三者耦合导致闭环极易发散——这次是真 bug，经系统标定（轮胎 c_α 70k→120k、转向作动器加一阶滞后+速率限幅）解决。

案例二 · 假警报

开环激励测试中，同一辆车"温和的正弦转向指令也会甩尾"，一度被记为"简化动力学模型低速数值发散"疑似 bug。深入复现后发现：模型里 throttle × v_max = 目标车速（这是速度指令，不是加速踏板开度），而激励模块用比例控制器 0.35×(目标车速 − vx) 在 vx≈0 时直接饱和到 throttle=1——相当于向模型下达"目标车速 ≈200 km/h"的指令，车辆当然甩尾。根因是节流阀语义理解错误，模型本身无需任何改动，改为开环 throttle = 目标速度 / v_max 后问题消失。

教训

"看起来像物理发散的现象，很多时候是驱动信号或控制器把手的语义用错了。"在断言"数值不稳定"之前，先确认输入激励本身是否合理——这条经验后来被专门记录下来，避免同类现象被反复误判。

02

潜伏两个月的数值稳定性 bug：轮速自旋积分失稳

埋于 v0.8.2修于 v0.9.0数值方法

发现契机

v0.9.0 做"完整性不够"的三视角系统审查，把负载页早在 v0.7.3 就补全的物理项（滚阻+风阻、气动升力、camber thrust、静态 toe）同步接入时域模型后，暴露出一个从 v0.8.2 起就已潜伏、近两个月未被发现的数值失稳。

根因

轮速自旋 ODE 的线性化模态 λ = c_κ·r²/(I_w·v)，在车速 v≤10 m/s 时，λ·h（h=5 ms 积分步长）超出 RK4 数值方法在实轴上的稳定域边界（约 2.78）。为什么两个月没被发现：此前时域模型在平路巡航工况下，稳态平衡点恰好是"零纵向力"，这个不稳定模态从未被真正激励起来——直到本版补入持续存在的纵向力（滚阻、风阻、坡道分量、加减速瞬态），才把这个原本静默的模态"唤醒"。

修复前 · 10 m/s 巡航轮胎纵滑率|κ| 振荡达 0.13–0.76
→
修复后 · 1–25 m/s 全速域稳态|κ| ≤ 0.002

解法

不是简单调小步长或加阻尼掩盖，而是把轮速自由度整体拆出两个时域模型的 RK4 状态向量，改用 model_core.semi_implicit_wheel_spin 半隐式积分——线性滑移区用后向欧拉（无条件稳定），摩擦饱和区（∂Fx/∂ω≈0）保持前向欧拉以避免隐式分母压制打滑本身。

意义

这是全项目最具"经典数值方法"色彩的一次调试——通过线性化求特征值、和标准积分方法的稳定域对比，精确定位问题根因，而不是靠试错调参。也提示一个通用教训："能跑"不等于"数值稳定"，尤其当某个自由度的失稳模态恰好被当前测试工况的平衡点掩盖时。

03

物理"重复造轮子"到统一底座，看见车速依赖

v0.8.0架构 / 建模保真度

问题一 · 物理散落五处

轮胎力、kingpin 转向力矩、载荷转移、bicycle 耦合这同一份物理，在三个时域模型（运动学/简化动力学/多体）加上准静态负载页、加上控制器，一共五个地方各写了一遍。任何一次修正都可能遗漏其中一处，不同实现之间会不知不觉产生偏差——后来 v0.9.0 才补齐的"时域/负载页物理割裂"问题，本质上正是这个根因的延续。

问题二 · 单轮 sweep 约掉了车速

负载分析页的核心工具此前假设"车身锁死直行"，即 α = −δ，把车速这个变量在数学上直接约掉了——图上完全看不到"高速时线性区收缩、转角-侧偏关系随车速变化"这一 4WIS 工程师非常关心的现象。

解法

新建 vehicle/model_core.py 作为唯一共享数学层（不依赖 simulator/controller/API/前端），三个时域模型和负载页全部改为调用它；同时把单轮 sweep 升级为真正的稳态 bicycle 耦合——对每个 (车速, δ) 求解 2×2 方程组（侧向力平衡 + 稳态横摆力矩平衡）得到车身姿态 (β, r)，再反推每个轮子的真实侧偏角。以 LS9 对称底盘为例，前左轮转 δ 时 α_FL ≈ −δ·(1/2 + mV²/(8·c_α·L))：增益随车速平方增长，从静止时的 0.5 一路涨到 50 km/h 时的 2.89，转向饱和点相应地从约 5.7° 收缩到约 1°。

协作花絮

这次重构是一次典型的多 AI 工具异步接力：用户离线期间，Codex 先完成了底座统一的基础工作；用户回来后，由 Claude 接力完成 W1 bicycle 耦合与数学模型讲解页，两段工作在同一版本内无缝衔接。

04

一个公式的三次迭代：kingpin 转向阻力矩的持续订正

v0.7.3v0.8.0v0.8.2物理公式复核

为什么难

主销转向阻力矩由多个物理项叠加（侧向力经力臂、纵向力经偏置、轮胎自回正力矩、载荷居中项等），任何一项的符号或量级错误都会让 δ_eq（自然回正角）这类关键工程结论产生偏差。这个公式在项目里被连续订正了三次，没有一次是推倒重写。

第一次 · v0.7.3 补项

发现驱动力经主销后倾角的二阶耦合项 Fx·r·tan(caster)·sin(δ) 此前被忽略，补入后公式在 δ=0 附近的斜率更真实。

第二次 · v0.8.0 删伪项

做统一底座复核时，发现另一项 −Fx·trail·sin(δ) 在几何上根本不成立——Fx 与 trail 方向平行，叉乘恒等于零，是一个"看似合理实则不存在"的伪物理项，直接删除。

第三次 · v0.8.2 交叉校验揪出对消 bug

依据姊妹项目《底盘与转向动力学讲义》参考《Steering Handbook》做数学口径复核时，发现气胎拖距 t_p 被结构性地计入了两次——一次悄悄并入 Fy 的机械力臂，一次又作为独立的自回正力矩 Mz 单独算了一次，两者符号相反、几乎完全抵消，且抵消在小转角区最严重——恰好是 δ_eq 工程结论最关心的区域。

意义

第三次订正如果没有姊妹项目独立理论写作过程"逼着团队把每个公式重新从教科书推一遍"的交叉校对，很可能会一直藏在代码里。这提示了一个方法论：多项叠加的工程物理公式，光靠单元测试的数值断言不够，还需要"从不同源头独立推导再对照"的复核方式。

控制回路代数环：后轮转向反馈模式的运动学振荡

v0.7.1控制系统调试

现象

v0.7.0 一口气实现了 4 种后轮转向（RWS）控制方法，其中 3 种（横摆反馈、稳态+瞬态、模型跟踪）在 v0.7.1 试用阶段被发现在运动学模型上剧烈摆动，实测幅值达 ±33°。

根因

运动学模型没有轮胎侧偏/滑移，车辆会瞬时精确执行任何转向指令并产生对应的横摆角速度。而这几种反馈策略的结构是 δr = g2·yaw_rate 这样的闭环——运动学模型下 yaw_rate 又几乎瞬时地由 δr 决定，于是 δr 与 yaw_rate 之间形成了一个没有阻尼、没有相位滞后的代数环，只要环增益大于 1，就会在正负限幅之间持续振荡、永不收敛。

解法

对反馈信号（横摆角速度、转角变化率）加一阶低通滤波（τ=0.08 s）引入相位滞后打破代数环，同时下调增益（g2 0.35→0.20、g_yaw 0.20→0.10），三档模型全部稳定，并补充运动学稳定性回归测试防止再犯。

意义

一个经典的"模型保真度反而暴露控制器设计缺陷"案例——运动学模型因为"太干净"（没有轮胎滞后这个天然的低通环节），把控制器本身缺乏阻尼的问题暴露了出来；在更真实的动力学模型上，轮胎滑移的滞后恰好掩盖了同样的设计缺陷。

安全研究方法论纠偏：两次被数据推翻的直觉

v0.13.0v0.14.0研究方法论

纠偏一 · 失效后的控制目标该是什么

团队最初尝试了一个"看起来更精确"的方案——用剩余健康轮反解出新的瞬心投影，让车辆整体运动尽量保持"无侧滑几何一致"。仿真数据显示，这个方案在直行工况下会让车辆退化为蟹行（5 秒横向漂移 31 米），过渡阶段横摆角速度 22°/s 反而超过不缓解时的基线 8°/s——方案被数据否决。真正有效的原则是反直觉的：失效后的控制目标应该是"路径保持"（力平衡），而不是"运动学一致"（零刮胎）。最终方案改为同轴镜像力抵消 + ESP 级横摆 PI，直接在力平衡层面稳定车辆。

纠偏二 · 可控性判据该用绝对值还是增量

最初想直接用侧向加速度 a_y 的绝对值作为可控性判据，但发现稳态过弯本身名义 a_y 就有 4.6 m/s²，会把正常过弯误判为失控（C3 级）。改为使用相对于同工况无故障参考的增量 Δa_y 才是正确判据。

意义

两条教训指向同一件事：直觉上"看起来更精确/更安全"的方案，在失效场景下反而是错的；唯一可信的仲裁者是仿真数据本身，方法论必须为数据让路，而不是反过来。

产品范式转型：从"实时驾驶仪表台"到"实验平台"

v0.9.0 诊断v0.10–0.12 落地产品架构

一句话诊断

把产品对标 CarSim/CarMaker 之后得出的结论："它们的'好用'不是皮肤，而是一整套工作流范式——一切皆数据集、试验是一等公民、求解器与界面解耦、每次运行留下可分析的结果资产。而当时的产品本质是一个'实时驾驶仪表台'，不是'仿真实验平台'。"

具体差距

机动（开环激励）此前完全跑在前端 wall-clock 定时器上——不可复现、不能批量；KPI 算在浏览器 30 秒环形缓冲区里——关掉浏览器就没了，无法跨版本回归比较；求解器只有"1 倍实时"一种形态，即便物理本身能跑到 100 倍以上实时。

推进方式

没有先急着重做界面（"UI 重构如果先做，只是给仪表台换壳"），而是先诊断出真正的根因——缺"实验(Experiment)→运行(Run)→结果(Artifact)"这条主干——批准清晰的 A→B→C 分期路线后再动手，且严格按既定顺序执行。Phase A 的验收标准是量化的：LS9 × {前轮转向, RWS 车速调度, 理想阿克曼} × ISO 双移线 @ 60/80/100 km/h 共 9 个 run 出 KPI 对比表、全程 < 1 分钟；实测 6-run DLC 矩阵 96 秒仿真只需 ≈4 秒墙钟，约 23 倍实时。

意义

一次"诊断先于开发"的范式转型样本——批准的分期路线全程没有因为"想先看到界面变化"而被打乱。

七、质量与可信度体系

docs/validation_matrix.md 明确声明"不是宣传材料"——它的作用是帮助后续开发判断哪些结论可以直接复用，哪些只能作为内部研究假设。

L0 概念有设计意图或界面入口，缺自动化验证
L1 单元核心函数或局部不变量有单元测试覆盖
L2 集成通过集成测试、smoke 或端到端人工验证
L3 参考对照与理论解、工程公式或独立工具做过定量对照
L4 实测对照与实车、台架或缩比验证平台数据做过定量对照
能力等级主要边界
运动学 4WIS 策略L3验证几何一致性与解析对照，不代表执行器/轮胎瞬态或实车精度
简化动力学模型L2已覆盖阻力/升力/toe/camber/坡道/载荷转移，仍缺外部车辆模型对照
多体动力学模型L214 DOF 工程近似，尚未与 CarSim/CarMaker 或台架数据对齐
轮胎与载荷敏感度L3c_α(Fz) 指数模型来自工程假设，缺同款轮胎实测曲线
主销/齿条负载分析L3LS9 参数与机构效率仍是标定快照
黄金实验回归L2覆盖 step steer / ISO 3888 DLC / 3 个单轮失效样本，仍缺外部基准

参考/外部/实测对照接入L3已有 2 个解析 benchmark；独立外部/实测来源仍为 0

八、遗留问题与后续规划

按 docs/v1_release_plan.md 与平台重构方案整理的未完成事项，均已有明确认领但尚未排期动手。

P1 · 外部对照（v1 唯一硬阻塞）

  • 已有 2 个解析 benchmark（稳态圆周、阶跃转向），仍缺 ISO 3888 双移线的外部对照
  • 需接入至少一个 CarSim/CarMaker 导出结果、公开基准或实测数据
  • L4 实测等级需等待台架或缩比车数据

物理深化（C3 后续）

  • 横向载荷转移仍按轴重 share 分配，未按防倾杆刚度分配（λf/λr）
  • 无制动模型，handbrake 字段贯通但无物理效果
  • 转向执行器力矩饱和闭环未做，torque_steer 目前只是诊断量
  • RWS 零侧偏比忽略前后配重差（Cf=Cr 简化假设）
  • 摩擦椭圆取 μx=μy，理论页已注明为口径选择

平台化 Phase B-3

  • dockview 自由布局（已批准但未引入，前端依赖列表中尚未出现）
  • per-channel 单位体系
  • ExcitationPanel / ScorePanel 降级为后端 KPI 的纯展示层

平台化 Phase C 剩余

  • C1 标准试验库（ISO 4138/7401/3888-2、蛇行、泊车机动）
  • C2 4WIS 专属分析页：执行器功率预算、ICR 可达域、摩擦利用率地图、失效模式批量矩阵
  • C4 稳定性边界自动图谱（不足转向梯度、横摆阻尼 vs 车速）
  • C5 单文件 HTML 报告导出

九、衍生成果

《底盘与转向动力学讲义》是从本项目土壤里长出的独立支线——给公司高管的底盘/转向动力学科普教材，同时兼做转向工程师"圣经级"参考书。两个项目共享同一套轮胎/载荷/主销/稳态横摆物理内核，互为验证。

交叉验证的价值已经兑现

正是这份讲义在复核《Steering Handbook》口径时，反过来发现了 4WIS Simulator 里 kingpin 力矩气胎拖距重复计算的对消 bug（v0.8.2，详见 §五「一个公式的三次迭代」）——独立支线项目不只是知识沉淀，也是本项目物理正确性的一道额外复核关卡。

十、总结与方法论

46 天、22 个版本、后端测试从 23 项涨到 245 项、浏览器端到端从 0 做到 50 个场景——这些数字背后是一条清晰的演进轨迹：从"能跑起来"（Phase 1-3）到"补齐需求、系统标定"（v0.4/v0.6）到"专项精修"（v0.7.x）到"统一物理底座"（v0.8.x）到"发现并修复潜伏问题、完成产品范式转型"（v0.9-v0.12）到"用平台做真研究"（v0.13-v0.14）到"交互化建模"（v0.15-v0.16），最终用近 100 次提交的"证明可信"收尾（v0.99.0）——每一个阶段都建立在对上一阶段诚实复盘的基础上。

贯穿全程的两条协作原则值得记录：其一，先完成计划内的开发，再做集成测试式排查——Phase 2/3 期间用户曾同时给出下一阶段开发任务和 5 个手测发现的问题，明确澄清后者是"整体集成测试时再调查"的参考，不是要求立刻停下手头开发；这套节奏后来一直沿用，避免了"边开发边救火"打乱交付节奏。其二，重大方向调整先出方案、审批后才实施——无论是 v0.7.0 后轮转向方法族的 ①→④→③→② 排序，还是 v1 平台重构的 A→B→C 分期与"Phase C 以 C3 物理深化优先"的优先级裁定，都是先形成书面方案交给用户确认，再严格按批准的顺序执行，中途不因为"想先看到某个效果"而打乱既定节奏。

项目当前的诚实定位：这是一个内部工程研究与预研分析工具，不是经过实车标定或认证的安全结论来源。它现在能做的，是把"4WIS 解耦控制"这个工程研究命题从"纸面推导"变成"可交互、可复现、可批量验证"的实验平台；它还不能做的，是替代台架、缩比车或实车数据——这一条边界，从 docs/validation_matrix.md 到 check_v1_readiness.py，被反复、诚实地写在每一处该写的地方。
